## 1. Verdict

**`PASS-WITH-GAPS`**

All eleven checklist dimensions (a–k) are satisfied at the level they were defined. The bundle is JSON-valid,
OpenAPI `3.1.0`, contains exactly the 15 required operations with unique IDs, resolves all 21 local `$ref`s, omits

self-test exit 0 with no network).

The gaps are structural, not evidential:

- **D1 (high, non-blocking):** `openapi.json:714` uses `"200 text/event-stream"` as a Responses-object key. This is
  not a legal OpenAPI 3.1 response-map key, so the SSE variant of `messagesCreate` is expressed non-conformantly and
  may be dropped or rejected by Apifox / strict validators. The two media types *are* present, but in the wrong place.
- **D2/D3 (medium, non-blocking):** the helper's optional `--input-mode object` does not match the documented Apifox
  `input` schema, and the bundled validator does not check response-map keys (which is why D1 went undetected).
- Four low-severity documentation/assertion imprecisions, plus one inherited reference-source inconsistency.

No fabricated evidence, no secret, and no live-authenticated claim was found. Nothing was modified except this file.

## 3. Defect list

### D1 — Illegal OpenAPI response key for the SSE variant (high, **non-blocking**)

- **Location:** `apifox/openapi.json:714` (`"200 text/event-stream": {`) inside `paths./v1/messages.post.responses`.
- **Observed:** OpenAPI 3.1 Responses Object keys must match `^[1-5](?:[0-9]{2}|XX)$` or be `default`. This key
  matches neither. A local scan flagged it as the only non-standard response key in the document.
- **Impact:** strict OpenAPI validators will reject the document; Apifox's importer may warn, skip, or mis-file the
  stream variant. The 15 operations themselves remain importable, so the export is still usable.
- **Evidence of the requirement being met conceptually:** `report:173-175` and `docs/02:487` correctly require two
  media types. The intent is right; the encoding is wrong.
- **Fix (one object restructure):** move `text/event-stream` under the existing `"200"` response's `content` map
  alongside `application/json`, and delete the extra response entry. No content changes needed.
- **Why non-blocking:** checklist (a)/(b)/(c) pass; both media types are materially present; no evidence is
  fabricated. But this should be fixed before final delivery.

### D2 — `--input-mode object` sends an undocumented payload shape (medium, non-blocking)

- **Location:** `apifox/push_apifox.py:268` (`payload_input = spec_text if args.input_mode == "string" else doc`) and
  `apifox/IMPORT.md:37-39`.
- **Official docs (re-fetched 2026-10-26):** `input` is `oneOf` a **URL object** (`url` required, optional
  `basicAuth{username,password}`) or a **string** ("JSON/YAML/X-YAML OpenAPI 数据字符串"). The spec *document*
  object emitted by `--input-mode object` is neither.
- **Impact:** latent only (default is `string`). If a user selects object mode, Apifox will likely reject the body.
- **Fix:** either drop `--input-mode object`, or make it emit `{"url": …}` and rename it `--input-mode url`.

### D3 — Validator does not check response-map keys, so self-test passes a non-conformant spec (medium, non-blocking)

- **Location:** `apifox/push_apifox.py:103-189` (`validate`), specifically the operation loop at `:137-139`, which
  checks only that `responses` is a non-empty dict.
- **Observed:** `--self-test` exits 0 on `openapi.json` even though it contains D1's illegal key. This is the root
  cause of the false reassurance in `IMPORT.md:263-264` ("15 paths / 15 unique operations / … resolve").
- **Fix:** add the `^[1-5]([0-9]{2}|XX)$|default` check and, optionally, require every response key to be a string.

### D4 — Idempotency mechanism asserted more strongly than the documentation supports (low, non-blocking)

- **Location:** `apifox/IMPORT.md:217-228`, key sentence `:219-220` ("Stable identity is the `operationId`. All 15 are
  fixed and unique, so Apifox matches existing endpoints rather than creating duplicates").
- **Observed:** the official import-openapi page documents `endpointOverwriteBehavior` and matching of "已有的接口"
  but does **not** state that `operationId` is the match key. In practice identical method+path under `AUTO_MERGE`
  should still converge, so the *outcome* claim is plausible, but "stable identity is operationId" is unverified.
- **Fix:** rephrase as "operationId keeps request/response identity stable; matching is expected on method+path under
  `AUTO_MERGE` (UNVERIFIED detail)".
- **Note:** `operationId` uniqueness *is* checked by the script (`push_apifox.py:141-149`), which is factual.

### D5 — `APIFOX_API_VERSION` listed as an environment variable but not read (low, non-blocking)

- **Location:** `apifox/IMPORT.md:86` (also `:83-86` table).
- **Observed:** `push_apifox.py:330` uses `default=DEFAULT_API_VERSION`, **not** `os.environ`. The row itself says
  "Not read from env by the script", so the contradiction is disclosed, but a variable/column-shaped table entry for
  a variable that cannot be used is confusing.
- **Fix:** remove the row or convert it to a note that only `--api-version` changes the header.

### D6 — `--self-test` silently ignores `--spec` (low, non-blocking)

- **Location:** `apifox/push_apifox.py:349-350`.
- **Observed:** `python3 push_apifox.py --self-test --spec /nope.json` exits 0 and validates the bundled
  `openapi.json` instead. This matches the guide's wording ("self-test of the bundled spec"), but the silent ignore
  can confuse CI users.
- **Fix:** honour `--spec` in self-test, or error when `--self-test` is combined with a non-default `--spec`.

### D7 — Model examples mix a client-facing alias into a target request schema (low, non-blocking)

- **Location:** `apifox/openapi.json:1207-1210` (`"examples": ["Iris-1.0", "DeepSeek-V4"]`).
- **Observed:** prior art maps `DeepSeek-V4 → Iris-1.0` *before* calling `/v1/messages` (`payload.go:75-89,91-97`;
  `report:332-352`). A direct consumer of this OpenAPI should send `Iris-1.0`, not the proxy alias.
- **Fix:** use only upstream IDs in examples (or label the alias as "proxy alias, resolved before dispatch").

### D8 — Asset path slash-form differs across artifacts (low, non-blocking, cross-artifact)

- **Locations:** `apifox/openapi.json:866` `/api/public-assets/` vs `docs/01-endpoint-catalog.md:391` and
  `docs/02-usage-semantics.md:490` `/api/public-assets`.
- **Observed:** both docs describe the *observed* request as the slash form returning 308. The OpenAPI models the
  observed slash path (correct); the docs' section titles use the post-redirect name (correct as the logical
  resource). Not a factual conflict, but it looks like one in an endpoint-count comparison.
- **Fix:** optionally add "(observed as `/api/public-assets/`)" to the two doc headings. `report:152` already shows
  both forms, so the report is unambiguous.

### Inherited reference-source inconsistency (informational, not an M4 defect)

- `report:57` and `report:388` say M1 used **54 total requests, ≤5 per endpoint**, anchored to
  `M1-anon-probe-matrix.txt:8,13`. The raw evidence line 13 does say "54 requests total … per-endpoint maximum 5".
  The consolidated `M1-index.md:21` still says "33 requests total, ≤3 per endpoint". **The report's numbers are the
  ones supported by the raw capture**; the index is stale. No M4 change required, but downstream summaries should
  follow the report/raw evidence, not `M1-index.md:21`.
